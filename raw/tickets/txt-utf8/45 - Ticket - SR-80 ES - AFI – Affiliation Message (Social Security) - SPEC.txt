        @Lily Li regarding the four AFI transaction types (MA/MB/MC/MG).
        These are not four new standalone reports. MA/MB/MC/MG are affiliation transaction
        types that share the vast majority of their fields — same worker identifiers, CCC, contract
        and group data — with only the operation type and a small set of event-specific fields
        differing. A single expanded spec under SR-80 covering all four would be the right
        approach if we proceed.
        That said, in standard Spanish payroll implementations these messages are not generated
        by the payroll engine. MA (Alta) and MB (Baja) fire in real-time when hire and termination
        events occur, and MC/MG fire on contract or contribution group changes — all of these
        are HR/onboarding system events, not payroll cycle events. Payroll typically has no
        involvement here.

        @Lily Li @Lily Li — addressing your three questions based on the actual spec (ES-AFI-
        001) and official SILTRA documentation:

          1. AFI FLOW — FROM WHOM TO WHOM

https://youtrack.hrblizz.dev/issue/SR-80                                                                  2/9
9/4/26, 3:03 PM                           ES: AFI – Affiliation Message (Social Security) - SPEC : SR-80

                 There is no direct API integration between HRB and TGSS for this file. SILTRA is a Java
                 desktop application — not a web service or API. The entire process is operator-driven and
                 manual.

                 The actual flow is:

                 • The operator opens the SILTRA desktop application (installed locally, authenticated via
                 SILCON digital certificate)
                 • The operator requests the TrabajadoresTramos file from TGSS — this step is optional
                 and informational; TGSS returns an XML file showing which workers and contribution
                 periods it has on record
                 • The operator downloads that XML file locally and imports it into HRB
                 • HRB reads the file, uses it as the instruction set to calculate the contribution bases, and
                 generates ES-BASES-001
                 • The operator then uploads ES-BASES-001 back to TGSS via SILTRA
                 • TGSS validates the bases file. If it doesn't match TGSS's records, TGSS sends back an
                 error file. If the operator doesn't send the confirmation file, TGSS closes the liquidation ex-
                 officio

                 So to directly answer your question: the report is NOT generated by HRB and uploaded to
                 TGSS. The TrabajadoresTramos (ES-AFI-001) is an inbound file that TGSS provides —
                 downloaded manually by the operator via SILTRA — not an automated inbound integration.

                  2. CONTRIBUTION BASE FIELDS — ARE THEY RELEVANT?

                 Yes, they are relevant and should stay in the spec. The DatosTramo/DatoSolicitado section
                 (base codes 500, 501, 502, 601, 602, 701, 702, 703) is how TGSS instructs the employer
                 which contribution bases to submit. TGSS populates these codes and mandatory
                 indicators (B/P) in the response file — HRB reads them and uses them as the basis for
                 preparing ES-BASES-001.

                 Key distinction: many fields in this spec are READ-ONLY — TGSS provides them (CAF,
                 DiasCotizados, Peculiaridades, DatoSolicitado values). Only the header fields (Autorizado,
                 ReferenciaExterna, CCC, period dates) originate from HRB.

                  3. MA / MB / MC / MG — ARE THESE IN THIS SPEC?

                 No. ES-AFI-001 (TrabajadoresTramos) covers the monthly contribution period file only. MA
                 (Alta), MB (Baja), MC (Cambio de Contrato), and MG (Cambio de Grupo de Cotización) are
                 separate real-time SILTRA event transactions — a completely different part of the SILTRA
                 system, not covered by this spec. Those would require a separate analysis and, if in
                 scope, a dedicated ticket.

                 On the earlier open question re Authorized User ID: the Autorizado field maps to
                 $legal_entity_hr.red_authorization_code — this is the RED system authorization number
                 that identifies the operator running SILTRA on behalf of the company. Not an API key. That
                 mapping is correct as already in the spec.

                 Wallisson dos Santos Gomes Commented 4 months ago
                 @Lily Li — to directly confirm: No, that conclusion is not correct. The spec IS still required
                 for product mapping, even though HRB does not generate this file.

                 Here is why:

                 The TrabajadoresTramos (ES-AFI-001) is officially classified by TGSS as a "Fichero de
                 Respuesta de la TGSS" — TGSS sends it to the user (employer/operator). HRB does not
                 generate it. That part is confirmed.

                 However, "not generated by HRB" does not mean "not in scope for product mapping."
                 Product mapping is required for both directions — files HRB generates AND files HRB
                 receives and processes.

                 This file is the trigger for the entire contribution base submission cycle:

                  1. Operator downloads TrabajadoresTramos XML from TGSS via SILTRA desktop app
                      (manual step — no API, no automated inbound integration)

                  2. Operator imports the file into HRB
                  3. HRB reads and parses it — specifically the DatosTramo/DatoSolicitado section, which

                      contains the base codes TGSS is requesting (500, 501, 502, 601, etc.) and the
                      mandatory/optional indicators (B/P)
                  4. Based on those codes, HRB calculates and generates ES-BASES-001
                  5. Operator uploads ES-BASES-001 back to TGSS via SILTRA

                 Without the spec, the dev team has no definition of what fields HRB needs to read from
                 the XML, what they mean, or how they map to HRB's internal data model. The spec is the
                 source of that mapping — even for an inbound file.

                 To summarize:

                      Not generated by HRB ✓ (confirmed)
                      Not an automated inbound API integration ✓ (confirmed — SILTRA is a Java desktop
                      app, not a web service)
                      Spec not required for product mapping ✗ (incorrect — HRB still needs to parse and
                      consume this file to drive ES-BASES-001 generation)

                 Hope this clarifies. Let me know if you have further questions.

                 Contract Type (TipoContrato) → $hr.contract_type_key

                 Occupation Code (Ocupacion) → $hr.occupation_code_cno

                 Province, CCC, Authorized User ID → all already in DD at legal entity level

                 CAF (Caf) — RA confirmed: TGSS-generated control code, must not be added to DD

                    as it determines the AT/EP rate

                    incentive programmes. If in scope, needs to be configurable per employee
